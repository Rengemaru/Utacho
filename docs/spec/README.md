## この仕様書の使い方

- リリースごとに1ファイルに分けている。**作業するときは、対象リリースのファイルだけを読み、そこに書かれた範囲以外のコードは変更しない。**
- 各タスクには「受け入れ条件」がある。すべて満たしたらタスク完了とする。
- 「⚠️ 未確認」「⚠️ 未確定」と書かれた箇所は推測で進めず、調査結果やオーナーの判断を待つ。
- コードを書く前の調査タスク（A1・D1）は**調査のみ**。修正はしない。

### 順番の理由

- **1.0.1 を先に出す**：テスターから「曲が登録しづらい」と要望が出ている不具合で、登録というコア機能を妨げているため。
- **1.0.2 を単独で出す**：API 35 の延長期限は **2026-11-01**。それ以降は API 36 でないと更新を配布できない。新フローと同時に出すと、不具合が出たときに原因が API 36 の挙動変更か新しいコードかを切り分けられないため分ける。
- **1.1.0 を最後に出す**：作業量が最も大きく（約33時間）、API 36 の上に載せる必要があるため。

## 全リリース共通のルール

### データベース
- 3リリースとも**DBスキーマは変更しない**。マイグレーションは追加しない。テスターの保存データに影響を出さないため。

### バージョン番号
- `app.json` の `version`（表示用 versionName）：1.0.1 → 1.0.2 → 1.1.0。
  - 末尾＝不具合修正、真ん中＝機能追加・画面変更、先頭＝互換性のない大きな変更（セマンティックバージョニング）。
- `android.versionCode`（内部用の整数）：**アップロードのたびに必ず前回より大きくする**。同じか小さいと Google Play が受け付けない。eas.json の自動採番設定を使うか手動で増やす。

### 配布（各リリース共通の C タスク）
| # | タスク | 受け入れ条件 |
|---|---|---|
| C1 | バージョン番号の更新 | versionName が対象リリースの値、versionCode が前回より大きい |
| C2 | ビルドとアップロード | EAS Build（AAB）→ Play Console の**クローズドテスト**トラックへ配布。トラックは停止しない（停止すると14日カウントがリセットされる） |
| C3 | リリースノートとテスター連絡 | 「いただいた要望を受けて改善しました」と具体的に記載。変更点をテストログにも残す（製品版アクセス申請の材料） |

### 完了の定義（全タスク共通）
- 受け入れ条件をすべて満たしている
- TypeScript の型エラーがない
- Android 実機で該当箇所を操作して確認した
- 変更に合わせて CLAUDE.md・Notion を更新した（または更新が必要な点を報告した）

## スケジュール上の注意

- 製品版の一般公開は **2026-11-01 前が目標**。14日満了 → 製品版アクセス申請（審査は最大7日程度）→ 製品版リリースの審査、の順に進むため、申請は遅くとも 10/20 頃までが安全圏。
- **1.0.1 の完成を申請の条件にしない**。14日が満了したら 1.0.1 の進捗に関係なく申請する。
